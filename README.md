# TradingApp-AWS

An event-driven order processing system, ported from an Azure/Service Bus original to AWS: ASP.NET
Core (`TradingApp.API`), AWS Lambda (.NET 8 isolated worker, `Amazon.Lambda.Annotations`), Amazon SQS
(FIFO queues), Amazon SNS (FIFO topic), and SQL Server. SQL Server runs **locally**, not on RDS — only
SQS and SNS are real AWS cloud resources; see [Local Development Harnesses](#local-development-harnesses)
below for why that split matters.

---

## Architecture Overview

```
POST /api/order
       │
       ▼
TradingApp.API ──► SQL Server (atomic Order + OutboxMessage via transaction)
                       │
                       ▼
       ScheduledOutboxMessageProcessor (EventBridge Scheduler, every 1 min)
         Phase 1: QuarantineExhaustedMessages()   (5 retries → quarantine)
         Phase 2: ProcessPendingMessages()          — claims a lease per message (ClaimedBy/ClaimedAt)
                  before sending, guarded by Polly retry + circuit breaker
         Phase 3: AutoRecoverResurrectedMessages() — resurrects quarantined messages once SQS is healthy
                       │
                       ▼
              CREATE_ORDER_QUEUE.fifo (Amazon SQS)
              MessageGroupId = ClientOrderId | CorrelationId as a MessageAttribute
                       │
                       ▼
          OrderExecutionProcessor (SQS trigger, ReportBatchItemFailures)
          Idempotent via ExecuteUpdateAsync(!IsProcessed)
          Randomly assigns ACKNOWLEDGED or REJECTED
                       │
                       ▼
              order_events_topic.fifo (Amazon SNS, FIFO)
              CorrelationId embedded directly in the OrderStatusEvent payload
              Sequence: 1 | MessageGroupId: ClientOrderId
              ├──► notification_queue.fifo    → NotificationProcessor
              ├──► risk_analysis_queue.fifo   → RiskAnalysisProcessor
              └──► audit_log_queue.fifo       → AuditLogProcessor
                       │
       ScheduledOrderStatusProcessor (EventBridge Scheduler, every 1 min, .Take(50))
       Promotes ACKNOWLEDGED → FILLED
       Publishes to order_events_topic.fifo: Sequence 2
       Falls back to UnpublishedTopicMessages on failure
                       │
                       ▼
       ScheduledUnpublishedTopicMessagesProcessor (EventBridge Scheduler, every 1 min)
       Retries failed topic publishes, Polly retry + circuit breaker, claim/lease guarded

CREATE_ORDER_QUEUE-DLQ.fifo (redrive after max receive count)
       │
       ▼
DeadLetterQueueProcessor (SQS trigger, ReportBatchItemFailures)
Persists to DeadLetterLogs, Teams webhook alert
```

All 5 SQS-triggered Lambdas (`OrderExecutionProcessor`, `DeadLetterQueueProcessor`,
`NotificationProcessor`, `RiskAnalysisProcessor`, `AuditLogProcessor`) return
`Task<SQSBatchResponse>` and report per-message `BatchItemFailures` via a shared
`TradingApp.Infrastructure.SqsBatchHandler` — one record failing no longer forces SQS to redeliver
the entire batch, including records that already succeeded. See
[SQS Partial-Batch-Failure Reporting](#sqs-partial-batch-failure-reporting) below.

AWS resources (queues, the SNS topic, subscriptions, DLQ redrive policies, `ReportBatchItemFailures`
on each event source mapping) are provisioned manually via the AWS Console/CLI — there is no
CloudFormation/SAM/CDK stack defining them; the `serverless.template` file in each Function project is
auto-generated by `Amazon.Lambda.Annotations` and only describes the Lambda function resource itself
(runtime, handler, memory, timeout), not its triggers.

## Lambda Functions

| Function | Trigger | Responsibility |
|---|---|---|
| `OrderExecutionProcessor` | SQS: `CREATE_ORDER_QUEUE.fifo` | Idempotent order processing, publishes `OrderProcessed` (Sequence 1) to `order_events_topic.fifo` |
| `ScheduledOutboxMessageProcessor` | EventBridge Scheduler: every 1 min | 3-phase: quarantine exhausted → claim + dispatch pending → auto-recover resurrected |
| `ScheduledUnpublishedTopicMessagesProcessor` | EventBridge Scheduler: every 1 min | Retries failed topic publishes from `UnpublishedTopicMessages`, claim/lease guarded, Polly retry + circuit breaker |
| `ScheduledOrderStatusProcessor` | EventBridge Scheduler: every 1 min | Promotes ACKNOWLEDGED → FILLED (`.Take(50)` per cycle), publishes `OrderStatusFilled` (Sequence 2) |
| `DeadLetterQueueProcessor` | SQS: `CREATE_ORDER_QUEUE-DLQ.fifo` | Persists dead-lettered messages to `DeadLetterLogs`, Teams webhook alert |
| `NotificationProcessor` | SQS: `notification_queue.fifo` | Sequence-ordered delivery (ACKNOWLEDGED before FILLED), Teams webhook |
| `RiskAnalysisProcessor` | SQS: `risk_analysis_queue.fifo` | Receives `OrderProcessed`/`OrderStatusFilled` events for risk scoring (stub — placeholder delay + random score, no real logic yet) |
| `AuditLogProcessor` | SQS: `audit_log_queue.fifo` | Receives events for audit logging (stub — placeholder delay, no real persistence yet) |

All 8 have a matching `*.LocalHarness` console app for local debugging — see below.

## Database Tables

7 tables, defined in `Database/TradingApp_Setup.sql`. Every table except `OrderNotificationSequences`
and `PendingFilledNotifications` carries a `CorrelationId` column (added for AWS-side CloudWatch
tracing) and a `ClaimedBy`/`ClaimedAt` pair (the claim/lease mechanism, see below).

| Table | Purpose |
|---|---|
| `Orders` | Core order records. `ClientOrderId` is the unique business key. `IsProcessed` guards idempotency. |
| `OutboxMessages` | Transactional outbox. Written atomically with `Orders`. Dispatched to SQS by the timer processor. |
| `QuarantinedOutboxMessages` | Messages that exhausted 5 retries. Auto-resurrected once SQS is healthy again. |
| `UnpublishedTopicMessages` | Failed `order_events_topic.fifo` publishes from `OrderExecutionProcessor`/`ScheduledOrderStatusProcessor`. Retried by a dedicated timer. |
| `DeadLetterLogs` | Persisted dead-letter messages from `CREATE_ORDER_QUEUE-DLQ.fifo`. |
| `OrderNotificationSequences` | Tracks last processed sequence number per order in `NotificationProcessor`, enforcing ACKNOWLEDGED-before-FILLED ordering. |
| `PendingFilledNotifications` | Persists out-of-order FILLED events so they survive process restarts, replayed once ACKNOWLEDGED lands. |

## Reliability Patterns

### Transactional Outbox

`POST /api/order` atomically inserts an `Order` and an `OutboxMessage` in one SQL transaction. The
outbox is the only path to SQS — nothing publishes directly from the API.

### Idempotent Processing

`OrderExecutionProcessor` uses `ExecuteUpdateAsync` with a `WHERE !IsProcessed` clause — a duplicate
message updates zero rows and exits cleanly, no double-publish.

### Claim/Lease Mechanism (`ClaimedBy`/`ClaimedAt`)

Because `ScheduledOutboxMessageProcessor` and `ScheduledUnpublishedTopicMessagesProcessor` run on
EventBridge Scheduler (a timer, not a queue trigger), overlapping invocations are possible if one run
takes longer than the schedule interval. Both processors atomically claim a row before acting on it —
`WHERE ClaimedBy IS NULL OR ClaimedAt < now - LEASE_SECONDS`, `SET ClaimedBy = context.AwsRequestId,
ClaimedAt = now` — via `ExecuteUpdateAsync`, the same atomic-update-as-guard pattern used for
`IsProcessed`. A message already claimed by a still-live invocation is skipped, not double-processed.
Each Lambda's configured timeout is set to comfortably exceed its own `LEASE_SECONDS` so a lease can't
expire and be re-claimed by a genuinely still-running invocation.

### Resilience Policies (Polly: retry + circuit breaker)

Registered via `TradingApp.Infrastructure.ServiceCollectionExtensions.AddResiliencePolicy(...)`. Two
independently-circuited policies exist per resource-touching Lambda, keyed by `ResiliencePolicyKey`
(`Sql` / `Messaging`) so a downed SQL Server can't trip the same breaker guarding an SNS/SQS call.
Each policy wraps a 3-attempt exponential-backoff retry inside a circuit breaker (opens after 3
consecutive failures, 2-minute cooldown). The retry predicate is split by domain:
`IsTransientAWSException` (checks `AmazonServiceException`, e.g. throttling/503/502/504/408) and
`IsTransientSQLException` (checks known-transient SQL Server error numbers) — both fall back to a
shared `AreThereAnyTransientHttpExceptions` check for generic HTTP-level transience. A small facade,
`IsTransientException(exception, policyKey)`, picks the right one; the call site hands
`Policy.Handle<Exception>` a lambda that closes over `policyKey` rather than a bare method group,
since the facade's own signature doesn't match `Func<Exception, bool>` directly.

### SQS Partial-Batch-Failure Reporting

All 5 SQS-triggered Lambdas return `Task<SQSBatchResponse>` via a shared
`TradingApp.Infrastructure.SqsBatchHandler.BatchSqsMessages(...)`, which wraps each record's
processing in its own try/catch and reports failed `MessageId`s in `BatchItemFailures` instead of
letting one bad record fail the whole invocation. Without this, SQS's default behavior redelivers the
**entire batch** on any uncaught exception — including records that already succeeded moments earlier
in the same loop. This was a real, not just theoretical, bug for `NotificationProcessor` specifically:
a redelivered already-processed ACKNOWLEDGED message would resend a live Teams notification, purely
because an unrelated order failed in the same batch. Each event source mapping must have
`FunctionResponseTypes: ["ReportBatchItemFailures"]` set (manually, via Console/CLI — see note above)
for the returned `BatchItemFailures` to actually be honored.

### Message Quarantine and Auto-Recovery

Messages that fail 5 dispatch attempts move from `OutboxMessages` to `QuarantinedOutboxMessages`.
`AutoRecoverResurrectedMessages()` resurrects them once SQS is reachable again, resetting retry count
and clearing `ProcessedAt` so they re-enter the normal dispatch pipeline on the next cycle.

`OutboxProcessingService` also has an alternate, currently-disabled worker-pool processing strategy
(`Channel<T>`-based, toggled via a `UseWorkerPoolProcessing` const, currently `false`) built and
verified as a hands-on concurrency exercise — see
`TradingApp-AWS/WorkerPoolStrategy.html` in the sibling `fis learning` docs folder for the full writeup
of both strategies side by side.

### Unpublished Topic Message Fallback

When `OrderExecutionProcessor` or `ScheduledOrderStatusProcessor` can't publish to
`order_events_topic.fifo`, the event is saved to `UnpublishedTopicMessages` with the `OrderStatus` at
the time of failure (not re-queried later, so a subsequent status change can't leak into a stale
retry). `ScheduledUnpublishedTopicMessagesProcessor` retries with the same claim/lease + circuit
breaker protection as the outbox processor.

### Sequence-Ordered Notification Delivery

FIFO `MessageGroupId = ClientOrderId` on `order_events_topic.fifo` guarantees ordered delivery per
order, combined with an explicit `Sequence` field on `OrderStatusEvent`:

- `OrderExecutionProcessor` publishes ACKNOWLEDGED/REJECTED with `Sequence = 1`
- `ScheduledOrderStatusProcessor` publishes FILLED with `Sequence = 2`
- If FILLED is processed before ACKNOWLEDGED has been recorded, it's persisted to
  `PendingFilledNotifications` (database, not memory — survives process restarts) rather than dropped
  or reordered in place
- Once ACKNOWLEDGED is processed, `NotificationProcessor` checks `PendingFilledNotifications`,
  replays FILLED immediately, and cleans up both tracking tables

### Teams Webhook Notifications

Two independent webhooks, not one shared URL like the original Azure version:
`TEAMS_NOTIFICATION_WEBHOOK_URL` (`NotificationProcessor`, every order status change) and
`TEAMS_DLQ_WEBHOOK_URL` (`DeadLetterQueueProcessor`, dead-letter alerts). Each posts a Teams message
card with the relevant order/correlation IDs.

## Local Development Harnesses

Every Lambda has a paired `*.LocalHarness` console app so it can run and be debugged **locally**
against the **real** cloud SQS/SNS resources and a **local** SQL Server — never a full cloud
deployment for day-to-day development. All 8 harnesses are built on two shared classes in
`TradingApp.LocalHarnessCore` (referenced only by `*.LocalHarness` projects, never by the real
`Functions/*` projects):

- **`SqsHarness.RunAsync`** — for the 5 SQS-triggered Lambdas. Polls the real queue directly
  (`ReceiveMessageAsync`), converts each `Message` to an `SQSEvent`, invokes the handler delegate, and
  deletes on success / leaves on failure for real SQS-driven retry semantics. Hardened against a
  crashed polling loop: `ReceiveMessageAsync` failures are caught separately from per-message
  failures, with `QueueDoesNotExistException` treated as fatal and `AmazonClientException` retried
  with a backoff delay rather than spinning or crashing the process.
- **`ScheduledHarness.RunAsync`** — for the 3 EventBridge-Scheduler-triggered Lambdas. Simple
  `while(true) { try { call handler } catch { log } await Task.Delay(1 min) }` loop — no SQS
  involved, deliberately simpler than `SqsHarness`.

Each `*.LocalHarness/Program.cs` builds its DI container via the **same** `Startup.ConfigureServices`
the real deployed Lambda uses (not a hand-copied subset), then resolves the real Lambda class via
`GetRequiredService<T>()` and hands its `FunctionHandler` in as the harness's delegate parameter — so
the harness never needs to know or duplicate a single Lambda's constructor shape, DI registrations, or
business logic. Run any of them with `dotnet run` from its own `Functions/*.LocalHarness/` directory.

## Distributed Tracing

There is no Application Insights on AWS — correlation instead flows through:

- `CorrelationId` generated in `TradingApp.API`'s `OrderService` via
  `Activity.Current?.TraceId.ToString() ?? Guid.NewGuid().ToString()`
- Persisted on the `Orders`/`OutboxMessages`/etc. rows (see table list above)
- Attached to outgoing SQS messages as a `MessageAttribute` (`CorrelationId`, `DataType: "String"`) —
  read back via `record.MessageAttributes["CorrelationId"]` on the consuming side
- Embedded directly on the `OrderStatusEvent` payload for the SNS hop — all topic subscribers read it
  from the deserialized payload, not from SNS message attributes
- Every Lambda logs `CorrelationId` as a structured field via `context.Logger.LogWarning`/`LogError`

Each Lambda function has its own CloudWatch Log Group (`/aws/lambda/<FunctionName>`) — sharing
`TradingApp.Infrastructure` code across functions does **not** merge their logs; whichever function's
execution environment is running when something logs is whose log group receives it. To trace a
failure: CloudWatch → Log groups → `/aws/lambda/<FunctionName>` → search all log streams for the
`CorrelationId` or `MessageId`.

## Event Contract

`TradingApp.Events` is a plain project reference here (not a versioned package via a private feed like
the original Azure repo's Azure Artifacts setup) — every consumer just references
`TradingApp.Events.csproj` directly.

```csharp
public class OrderStatusEvent
{
    public Guid ClientOrderId { get; set; }
    public required string Status { get; set; }
    public DateTimeOffset EventTime { get; set; }
    public int Sequence { get; set; }
    public string CorrelationId { get; set; } = string.Empty;
}

public class OrderPayload
{
    public Guid ClientOrderId { get; set; }
}
```

`OrderPayload` is used for `CREATE_ORDER_QUEUE.fifo` messages. `OrderStatusEvent` is used exclusively
for `order_events_topic.fifo` messages.

## Simulation Methods

Each function that publishes/receives real messages includes simulation flags for demo and testing,
all no-ops when passed `false`:

| Method | Location | Effect |
|---|---|---|
| `SimulateQueueFailure(bool)` | `ScheduledOutboxMessageProcessor` | Forces a queue-send failure to trigger the circuit breaker |
| `SimulateTopicFailure(bool)` | `OrderExecutionProcessor`, `ScheduledOrderStatusProcessor`, `ScheduledUnpublishedTopicMessagesProcessor` | Forces an SNS publish failure to trigger the circuit breaker / populate `UnpublishedTopicMessages` |
| `SimulateRedirectToDeadLetterQueue(bool)` | `OrderExecutionProcessor` | Throws on message receipt so SQS eventually redrives the message to the DLQ |

Simulation counters use `static int` fields so they persist across repeated invocations within one
warm Lambda execution environment.

## Local Setup

### 1. Database

Run `Database/TradingApp_Setup.sql` against a local SQL Server instance — creates the `TradingApp`
database with all 7 tables, indexes, and constraints.

### 2. Environment variables

For the **Lambda functions** — no Key Vault/Secrets Manager, everything is a plain environment
variable, read via `Environment.GetEnvironmentVariable(...)`:

| Variable | Used by |
|---|---|
| `SQL_CONNECTION_STRING` | Every Lambda function touching SQL Server |
| `CREATE_ORDER_QUEUE_URL` | `ScheduledOutboxMessageProcessor` |
| `ORDER_EVENTS_TOPIC_ARN` | `OrderExecutionProcessor`, `ScheduledOrderStatusProcessor`, `ScheduledUnpublishedTopicMessagesProcessor` |
| `TEAMS_NOTIFICATION_WEBHOOK_URL` | `NotificationProcessor` |
| `TEAMS_DLQ_WEBHOOK_URL` | `DeadLetterQueueProcessor` |

(`NotificationProcessor`, `RiskAnalysisProcessor`, `AuditLogProcessor`, `DeadLetterQueueProcessor`
consume their own SQS queue directly via the Lambda trigger / local harness poll — no queue URL env
var needed on the consuming side.)

**`TradingApp.API` is the one exception** — it used to load config from a real Azure Key Vault via
`DefaultAzureCredential` (a stale leftover from the original Azure clone that meant it couldn't start
without an `az login` against a specific Azure AD tenant), migrated 2026-08-04. It now fetches
`SQL_CONNECTION_STRING` from **AWS Secrets Manager** at startup (`Program.cs`, secret name
`TradingApp/SqlConnectionString`, region `eu-north-1` — same region as the SQS/SNS clients) and sets
it as an environment variable before calling the same `AddTradingDbContext()` extension every Lambda
uses — so the DB-context registration itself is identical everywhere, only *where the value comes
from* differs for this one project. Application Insights was removed outright, not replaced — there's
no AWS equivalent wired up (CloudWatch via each Lambda's own logging is the AWS-side tracing story,
see Distributed Tracing above; `TradingApp.API` itself has no request-level tracing today).

### 3. Run

Preferred day-to-day workflow — run any `*.LocalHarness` project directly:

```
cd Functions/OrderExecutionProcessor.LocalHarness
dotnet run
```

This runs the real Lambda class locally, against the real SQS/SNS resources and your local SQL
Server, fully debuggable in an IDE. See [Local Development Harnesses](#local-development-harnesses)
above. A full cloud deployment (`dotnet lambda deploy-function` or equivalent) is only needed to
verify the actual deployed artifact, not for routine development.

## Notes

- SQL Server and AWS credentials are the only two things every Lambda function/harness needs locally —
  no Key Vault, no Secrets Manager, no Application Insights for those. `TradingApp.API` is the
  exception: it needs AWS credentials with `secretsmanager:GetSecretValue` on
  `TradingApp/SqlConnectionString` to start at all (see Environment Variables above)
- `AmazonSQSClient`/`AmazonSimpleNotificationServiceClient` use the default AWS SDK credential chain —
  no explicit key/secret wiring in code
- `RiskAnalysisProcessor` and `AuditLogProcessor` are currently stubs (a placeholder delay and, for
  risk analysis, a random score) — no real persistence or logic yet, so message redelivery is
  harmless today but not because of any actual idempotency guard
